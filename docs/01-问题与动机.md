# 01 问题与动机

## 两个系统，两套互不可见的记忆

这台机器装了两个系统，同一时刻只能跑一个。Windows 在 NTFS 分区上，Ubuntu 在 ext4 分区上。

Claude Code 的记忆库默认落在自己那边的用户目录里。Windows 那份在 C 盘，Ubuntu 那份在 ext4 分区，
两边文件系统互不相识，也没有一个能同时被两边挂载的位置。换一次系统，前面教过的东西就等于清零。

这不只是多做一遍无用功。教第二遍的时候，人不会一字不差地重复第一遍的说法，而两边的 Claude
各自把自己听到的版本写了进去。两份记忆从此并行生长，谁也不知道对方存在。

## 一次具体的翻车

2026-10-01 之前，两个系统各有一份关于硬件时钟的约定。Windows 侧记的是把硬件时钟当本地时间处理，
Ubuntu 侧记的是把它当 UTC。两份记忆各自内部自洽，照着自己那份做都不会当场报错，可两边对同一个
硬件时钟的理解差了整整 8 小时。

切一次系统，时间就不对。更绕的是，两边的手册都写着「时间不对是正常现象，改一下就好」，
于是每一次都被当成新问题重新处理一遍。查日志、怀疑主板电池、怀疑时间同步服务。这些方向都试过。
真正的根因始终是那个谁都没想到的方向，两边记的约定不一样。

问题不在某一条记忆写错了。两条记忆各自都对，错的是它们被分别写在了两个读不到彼此的角落里。

## 这套框架要达成的

把「换个系统还成立」的知识集中到一个两个系统都能读写的地方，只存一份。这样教一次就够，
而且不会长出第二个版本。

顺带还有个收益。那些知识第一次有了统一的家，原先它们散在各自的记忆目录里，谁在哪个系统上
遇到过什么就记在那边。同一条踩坑经验可能在两边分别记过，措辞还不一样。

## 不打算解决的

这套框架只管记忆放在哪、怎么组织、按什么规矩写。它管不了记忆的内容质量。一条只记录「装到哪一步了」
的记忆，放进再合理的目录结构里也还是会过期，然后被当成事实引用。
