# 03 接任务先路由

这一篇是整套框架的核心动作。

## 为什么不能全读

记忆分了层，但每次任务都读三层是不划算的。三层加起来几十条，其中大部分跟眼前这件事无关，
读完既费 token 又稀释注意力。反过来，只读自己那层也有风险，跨系统的任务会漏掉另一半。

所以先判载体，只读该读的。

## 第一步，判断任务载体

| 载体 | 读哪几层 | 典型任务 |
|---|---|---|
| Windows 专属 | 通用 ＋ Windows | Windows 上的编译、外设、系统设置 |
| Ubuntu 专属 | 通用 ＋ Ubuntu | ROS、apt 源、装机、Linux 键盘驱动 |
| 跨系统 | 三层全读 | 共享盘上的工具链、技能库、双系统时间、这套记忆架构本身的维护 |
| 纯通用 | 只读通用 | 写材料、改稿、跟系统无关的问答 |

判不准的时候按「跨系统」处理，多读一层的代价小于答错的代价。

## 第二步，先说一句

在动手之前，用一句话说清读了哪几层。例如「这是 Windows 任务，我读了通用加 Windows」。

这句话是给用户看的。用户据此能立刻发现读错了地方，不必等到答案跑偏才回头排查，而这句话本身的
成本几乎为零。一个常见的情形是任务开头看着像 Ubuntu 的，做着做着发现要动共享盘上的东西，
这时补一句「这个要跨到 Windows 层去查」，比闷头做完再解释要省事。

## 第三步，判断该调哪个 skill

每条消息都附带了当前可用的技能列表，扫一眼即可，不需要去翻文件系统。

有对得上的就直接用，并且把判断说出来，一句话就够，例如「这个用 `markitdown` 更合适」。
把判断说出来的理由和上一步相同，用户要看得见这个决策发生了。

没有合适的就正常做。为了凑而硬套一个 skill，比不用更费 token，效果还更差。

一个任务里如果分成几段、每段适配的技能不同，就分段判断，不要只看开头那一段。

## 第四步，执行，然后把新规矩写回去

任务做完，如果过程中定下了新规矩，写回它该去的那一层。

- 换个系统还成立，写通用层
- 只在某一个系统成立，写该系统层
- 写完在该层 `MEMORY.md` 的索引里加一行

判断写不写、写在哪，见 [05-写记忆的规矩.md](05-写记忆的规矩.md)。

## 这条规矩本身也该守

框架的维护也要走这四步。维护这套记忆架构属于跨系统任务，读三层。改动完索引和条目之后，
两个系统层的颗粒度要保持一致，否则下一次跨层查找会先被结构差异绊一下。
