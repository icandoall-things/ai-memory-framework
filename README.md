# 双系统 AI 记忆架构

一台机器上装了 Windows 和 Ubuntu，两边各跑一个 Claude Code。两个系统不能同时开机，各自的记忆库
躺在各自的分区上，一边的 Claude 读不到另一边记了什么。

结果是重复教学。同一句「跑 Python 用哪个解释器」在 Windows 上教过，重启进 Ubuntu 还得再教一遍。
比重复更麻烦的是版本漂移，两边对同一件事的记忆可能互相打架，而两边都以为自己是在照规矩办事。

这套框架把记忆按「换个系统还成立吗」拆成三层，全部放在两个系统都能读写的盘上。两边的全局记忆
文件退化成两行 `@引入`，具体内容一概不放本地。

> **在线看效果图** <https://icandoall-things.github.io/ai-memory-framework/>
> —— 三层架构的可视化图，浏览器直接打开，自带深色模式。

## 三层结构

```
D:\AI-MEMORY\
├── 通用MEMORY\      ← 两个系统都加载
├── WindowsMEMORY\   ← 只有 Windows 加载
└── UbuntuMEMORY\    ← 只有 Ubuntu 加载
```

| 层 | 自动加载于 | 装什么 |
|---|---|---|
| 通用 | 两个系统 | 换系统仍然成立的规矩，比如沟通风格、记忆写法、工具存放位置 |
| Windows | Windows | 只在这个系统上做的事，比如 Windows 的命令行与外设踩坑 |
| Ubuntu | Ubuntu | 同上，Ubuntu 侧的那些，比如装机约束、apt 与镜像源 |

分层的判定只有一句话。**换到另一个系统，这条还成立吗。** 成立就进通用层，不成立就进各自那层。

分层只决定「哪几层被自动加载」。三层文件都在同一个盘上，两个系统都读得到。任务做到一半发现
需要别层的知识，随时跨层去读，说一声即可，规则不必写死。

## 接任务先路由

每次接到任务，先做完四件事再动手。

1. 判断任务载体属于 Windows 专属、Ubuntu 专属、跨系统，还是纯通用
2. 说一句读了哪几层，例如「这是 Windows 任务，我读了通用加 Windows」
3. 判断该调哪个 skill，先把判断说出来再调
4. 干完有新规矩就写回对应那层，并在该层 `MEMORY.md` 里加一行

第二、三步是做给人看的。用户需要知道这件事是按哪几层的知识办的，也需要知道为什么动用了某个 skill。
细则见 [docs/03-接任务先路由.md](docs/03-接任务先路由.md)。

## 怎么接上

1. 把 `template/` 里的三层目录复制到那个共享盘，例如 `D:\AI-MEMORY\`
2. 改两个系统的全局记忆文件，各写两行引入。Windows 引「通用 ＋ Windows」，Ubuntu 引「通用 ＋ Ubuntu」
3. 以后新记忆写进对应层的域子目录，一条一主题，顺手在索引里加一行

接线命令、目录联接的建法、盘没挂载时会发生什么，都在 [docs/06-接线与坑.md](docs/06-接线与坑.md)。

## 目录里有什么

| 路径 | 内容 |
|---|---|
| `docs/` | 六篇说明，从动机一路讲到接线 |
| `template/` | 可以直接复制的空骨架，不含任何真实条目 |
| `assets/三级架构效果图.html` | 三层架构的可视化图，浏览器直接打开，自带深色模式。也可[在线看](https://icandoall-things.github.io/ai-memory-framework/) |

## 这套东西的边界

它解决的是两个系统各记各的、换个系统就要把规矩重讲一遍的问题。它不解决记忆本身写得好不好。
一条只描述此刻状态的记忆，放在哪层都会烂掉。记忆该怎么写，见
[docs/05-写记忆的规矩.md](docs/05-写记忆的规矩.md)。
